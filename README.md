# Magnetic Confinement Configurations

An interactive 3D visualization of current-carrying filaments for exploring magnetic confinement geometries in plasma physics.

## Overview

This project provides a collection of simplified coil configurations inspired by magnetic confinement systems used in plasma physics.

Each configuration is represented by a set of current-carrying filaments in three-dimensional space. The geometry, relative positioning, and model current values can be adjusted to explore different coil arrangements and their underlying physical principles.

The project is intended as an educational and exploratory tool for students, educators, and anyone interested in the geometry of magnetic confinement systems.

## Available Configurations

- **Ioffe–Pritchard trap** — a magnetic trap combining Ioffe bars and pinch coils.
- **Yin–Yang coils** — an interlocking coil geometry used to explore compact magnetic confinement configurations.
- **Mirror and cusp traps** — configurations illustrating magnetic mirrors and the role of parallel and antiparallel coil currents.
- **Cloverleaf coils** — a four-loop geometry for exploring multipole-like magnetic configurations.
- **Baseball coils** — a compact coil geometry associated with minimum-BB magnetic configurations.
- **Torsatron** — a helical coil configuration for exploring three-dimensional magnetic geometries.
- **Tokamak D-coils** — toroidally arranged D-shaped coils representing a simplified tokamak coil system.

The configurations are idealized geometric models. They are intended to illustrate coil arrangements rather than reproduce every engineering detail of real magnetic confinement devices.

## How It Works

Each configuration generates a collection of filaments. A filament is defined by:

- A sequence of three-dimensional points describing its geometry.
- A model current value, including its sign to represent current direction.
- An optional color for visual identification.

The filaments are rendered as three-dimensional tubes using [Three.js](https://threejs.org/).

Colors can be assigned individually to distinguish coils and configuration components. If no color is specified, a default color is used.

The current values and geometric parameters used in the visualization are model parameters. They should not automatically be interpreted as physical quantities expressed in SI or CGS units.

## Magnetic Field Calculation

The magnetic field generated by a current-carrying filament can be described by the Biot–Savart law.

In the Gaussian CGS system, for a steady current in vacuum, the law can be written as

$$
\vec B(r) = \frac{I}{c}\int \frac{d\vec{\ell}'\times(\vec r - \vec r')}{|\vec r - \vec r'|^3}
$$


where:

- $\vec B(\vec r)$  is the magnetic field at the observation point.
- $\vec r$  is the observation point.
- $\vec r′$ is a point on the current-carrying filament.
- $d\vec {\ell}'$   is a directed line element along the filament.
- $I$  is the electric current in Gaussian CGS units.
- $c$ is the speed of light in vacuum.

For a configuration consisting of multiple filaments, the total magnetic field is obtained by superposition:

$$
\vec B_{total}(\vec r) = \sum^{N}_{k=1}\vec B_k(\vec r)
$$

Numerically, the field can be evaluated by discretizing each filament into short line segments and summing their contributions.

In order to visualize the magnetic field we make line tracing by solving the equation

$$
\frac{d\vec r}{ds} = \frac{\vec B(\vec r)}{|\vec B|}
$$

using the Euler or Runge-Kutta 4th methods. 

In order to accelerate calculation of streamlines the field is first calculated on the grid $32\times 32 \times 32$ and then interpolated linearly at particles positions. 
Initial seeds for streamlines are arranged on the spheres of small radius according the Fibonacchi ordering. 

### Scope of the Current Implementation

The current 3D visualization focuses on coil geometry, spatial arrangement, and visual identification of individual filaments.

The geometric and current parameters used here are model values for visualization. They are not, by themselves, a complete physical specification of a magnetic confinement system.

Quantitative magnetic-field calculations using a consistent CGS unit system are intended to be handled separately, for example in a Python-based computational component.

The Biot–Savart formulation above describes the physical basis for such calculations; its inclusion in this documentation does not imply that a validated magnetic-field solver is already implemented in this project.

## Educational Applications

The project can be used to explore:

- The geometry and symmetry of magnetic confinement configurations.
- The relationship between coil arrangement and magnetic-field structure.
- The effect of reversing the direction of current in individual coils.
- Differences between axisymmetric and three-dimensional coil arrangements.
- The geometric principles behind tokamaks, stellarators, magnetic mirrors, and cusp traps.

It can serve as a starting point for further numerical investigations, including magnetic-field visualization, field-line tracing, and the analysis of magnetic minima, provided the corresponding computational methods are implemented.

## Limitations

This project is an educational visualization tool, not a validated engineering or scientific simulation package.

In particular:

- Coil geometries are simplified and may differ from real device designs.
- Model parameters are not necessarily expressed in physical units.
- A visual representation of coils does not establish the accuracy of the resulting magnetic field.
- The visualization alone does not demonstrate stable plasma confinement or predict experimental performance.
- Quantitative results require appropriate physical units, numerical methods, validation, and, where relevant, additional plasma physics models.

The software is provided for learning, experimentation, and exploratory visualization. It should not be used as the sole basis for engineering decisions, experimental design, safety-critical applications, or quantitative scientific conclusions.

## Building and Deployment
### Production Build

To build the application for production, run:

<pre>
npm run build
</pre>

The generated files are placed in the dist/ directory.

To test the production build locally, run:

<pre>
npm run preview
</pre>

## Deploying to GitHub Pages

This project uses gh-pages to publish the production build to GitHub Pages.

First, build the application and deploy it:

<pre>
npm run build
npm run deploy
</pre>

The deployment script publishes the contents of dist/ to the gh-pages branch.

Before deploying, make sure that:

- The gh-pages package is installed.
- The base option in vite.config.ts matches the repository's published URL.
- GitHub Pages is configured to serve the gh-pages branch from the root directory.

After deployment, open the GitHub Pages URL and verify that the application loads correctly.

For more information, see the Vite deployment guide and the gh-pages documentation.

## Development Best Practices

When experimenting with the project, it is good practice to separate development, testing, and deployment.

- Experiment locally first. Use npm run dev to modify coil geometries, current values, colors, and visualization parameters without affecting the published website.
- Test your changes. Check the application in the browser and verify that your modifications behave as expected.
- Build before deploying. Run npm run build to check that the project compiles successfully.
- Preview the production build. Use npm run preview to inspect the built application before publishing it.
- Deploy only when ready. Run npm run deploy when you are satisfied with the results. This publishes the contents of dist/ to GitHub Pages.
- Keep changes manageable. Make small, focused changes so that unexpected behavior is easier to identify and fix.
- Use version control. Commit working changes regularly with descriptive commit messages. Consider using a separate Git branch for larger experiments.
- Avoid committing generated files unnecessarily. Follow the repository's .gitignore rules and keep dependencies managed through package.json and package-lock.json.

A recommended workflow is:

<pre>
npm run dev
</pre>

# Experiment and test locally; stop the server when finished.

<pre>
npm run build
npm run preview
</pre>

# Verify the production build.

<pre>
npm run deploy
</pre>

# Publish when everything looks good.


*Remember*: the published website is a demonstration of the current project, not a guarantee that every configuration is physically accurate or suitable for quantitative scientific use.
